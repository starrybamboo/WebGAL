## Issue 正文中的基线

Issue 正文标题为“RFC 0005：WebGAL 静态组合立绘”，目标是合并到 WebGAL 主分支，并以 4.6.2 的立绘行为为基线。正文开头已经声明：

> `composeFigure` Demo、`-composite` 参数为个人维护的立绘合成分支的实验性命令，如果看到请无视~~

正文提出的原始模型包括：

- 使用 `game/figure/<角色模板选择符>/figure.json` 声明画布、静态图片部件和递归预设。
- 使用 `changeFigure:<角色模板选择符>/<组合列表>` 请求组合。
- 先将有序部件合成为一张静态图，再交给现有普通图片立绘系统。
- 默认使用本轮合成立绘缓存，并规划可选的 `localforage` 持久化缓存和预热机制。
- 组合状态保存逻辑 URI；正文原方案要求读档等待组合准备完成后再继续。
- 正文原方案明确“不引入角色自动管理”，无 `-id` 时继续使用左、中、右槽位，有 `-id` 时使用自由立绘目标。

这些内容是评论出现前的 RFC 基线；下节列出的评论决策会覆盖其中与角色管理、持久化、读档等待和脚本入口冲突的部分。

## 指定评论的明确决策

以下内容直接来自评论原文，按评论中的五点整理。

### 1. 角色管理对象改为“角色”，引入 `character` script

评论给出的示例是：

```webgal
character: yuki -preset=summer_uniform -left;
```

评论明确要求：

- 角色管理操作的目标对象是“角色”，不再只把组合结果当作一次 `changeFigure` 目标。
- 后续调用 `character: yuki` 时，同名角色在舞台上只能同时出现一个。
- `character` 支持 `figure` 支持的几乎所有变换、效果和动画机制。
- 底层仍然使用 figure，但对外以角色为对象管理。

这意味着组合立绘的正式脚本入口应从“扩展 `changeFigure` 语法”转向新增 `character` 命令；合成结果进入 figure 控制系统后仍可复用 figure 的演出能力。

### 2. 暂不考虑持久化缓存

评论明确写明：

> 暂不考虑持久化缓存，在浏览器实现这个策略很复杂。

因此，RFC 中关于 `localforage`、磁盘/浏览器持久化 WebP、持久化开关、回填、持久化清理和浏览器原生 WebP 编码限制的内容，不应继续作为首期已承诺范围。评论没有否定进程内缓存；它只明确暂不做持久化策略。

### 3. 读档不等待组合准备

评论明确否定“恢复舞台时等待所需组合准备完成后再继续游戏”：

> 不需要，和现有的立绘网络请求逻辑采用同一方案，即便立绘未加载，也不阻塞游戏流程。

所以组合图片的加载/合成应沿用普通立绘网络请求的非阻塞模型。读档先恢复舞台和脚本流程，图片在可用时由现有立绘控制系统完成显示；不能因为组合纹理未准备好而阻塞整个读档或游戏继续执行。

### 4. `.json` 误认问题由新的脚本入口降低风险

评论的理由是：

> 由于采用新的 character 脚本，应该不需要太担心 .json 被误认的问题，因为立绘合成后就是普通图像，进入立绘控制系统的时候按普通图像处理即可。

评论的核心边界是：`figure.json` 是组合定义的输入，不应作为最终进入 figure 控制系统的立绘资源；合成完成后得到普通图片，后续按普通图片处理。新增 `character` 命令也使组合解析不必依赖把 `.json` 伪装成普通 `changeFigure` 图片路径。

评论没有规定引擎是否每次读取模板、模板缓存如何失效、模板文件路径是否必须固定，也没有决定旧 `changeFigure` 组合语法是否保留；这些仍是 RFC 需要另行确定的事项。

### 5. 为后续“只切换部件”预留组件变体

评论提出后续可能支持只改变角色立绘的某个部件（例如只切换表情），并给出了扩展 `components` 的草案：

```json
{
  "components": {
    "face": {
      "smile": {
        "src": "faces/smile.webp",
        "x": 0,
        "y": 0,
        "scale": 1
      },
      "sad": {
        "src": "faces/sad.webp",
        "x": 0,
        "y": 0,
        "scale": 1
      }
    }
  }
}
```

这个草案把 `face` 作为组件组，把 `smile`、`sad` 作为该组的变体；它不同于正文中 `components` 的“名称直接映射单个部件”结构。评论只提出方向和示例，没有决定：

- 预设如何选择一个组件组的变体；
- 未指定变体时是否有默认值；
- 是否允许多个组同时没有选择；
- 后续脚本采用什么参数更新单个变体；
- 变体切换是否重新合成整张图、是否复用已有部件纹理；
- 变体名称与当前部件/预设名称空间如何兼容。

因此，组件变体应记录为后续扩展方向，不应在首期实现中擅自推导出完整语义。

## 对 RFC 的直接影响

下表区分“评论明确要求”与“需要在 RFC 中继续设计”的内容：

| 主题 | 评论明确要求 | RFC 仍需确定 |
| --- | --- | --- |
| 脚本入口 | 新增 `character` script；示例为 `character: yuki -preset=summer_uniform -left;` | `character` 的完整语法、参数解析、与现有 `changeFigure` 的兼容关系 |
| 管理对象 | 以角色为对象；同名角色舞台上只能同时出现一个 | 角色唯一性的索引范围、`-id` 如何处理、清除/替换规则 |
| figure 能力 | 支持 figure 的几乎所有变换、效果、动画机制；底层仍是 figure | 哪些参数首期确实可复用，组合完成前后的动画时序和错误处理 |
| 合成输出 | 合成后按普通图像进入立绘控制系统 | 输出 URL/Blob 生命周期、加载失败表现、缓存键和进程内缓存细节 |
| 持久化缓存 | 首期暂不考虑 | 是否保留未来扩展点，何时重新评估浏览器持久化 |
| 读档/网络请求 | 不等待组合准备，沿用普通立绘非阻塞逻辑 | 读档时舞台状态如何标记“正在加载”，以及加载完成后的切换演出 |
| `.json` 处理 | 组合定义不作为最终立绘；合成结果按普通图片 | 模板读取和缓存策略，以及普通资源路径判定的具体实现 |
| 组件变体 | 为后续单独切换部件预留 `components.<group>.<variant>` 结构方向 | 变体选择、默认值、脚本语法、预设与缓存语义 |

## 仍未决的关键问题

这些问题在 Issue 正文和指定评论中都没有给出答案，不能从评论直接推断：

1. **`character` 与现有 `changeFigure` 的边界**：普通图片、Live2D、Spine 和静态组合是否都能由 `character` 统一引用；已有 `changeFigure` 是否继续作为底层/兼容入口。
2. **角色唯一性模型**：同名角色只能出现一次时，角色名是否就是唯一键；显式 `-id` 是否允许多个实例；角色移动位置或替换立绘时如何维护唯一索引。
3. **预设参数的表达**：示例使用 `-preset=summer_uniform`，但正文曾使用路径加组合列表。需要确定一个正式 ABI，不能同时假定两套语法都存在。
4. **角色模板文件的生命周期**：模板是否只在首次使用时读取并缓存；Terre 保存或预览同步时如何失效模板和组合缓存；外部修改资源如何发现。
5. **进程内缓存范围**：评论只排除持久化缓存，未决定是否做内存缓存、缓存上限、并发合成去重和快进时任务替换。
6. **非阻塞加载的显示策略**：旧角色图像是否保持显示、首次出场保持为空还是显示占位图，以及合成失败是否只记录日志并保留旧图。
7. **变体结构兼容性**：从扁平 `components[name]` 迁移到分组 `components[group][variant]` 是否需要新 `Version`，以及如何表达组件组的层级顺序、位置和默认变体。
8. **Terre 交付边界**：评论没有提到编辑器、导出校验、预览同步和共享规则包是否首期实现，仍需单独确认。

## 结论

Issue #1010 的指定评论是对原 RFC 的产品方向修正，而不是对原文的逐字批准。可以高置信度纳入首期基线的只有四点：引入以角色为对象的 `character` script；同名角色舞台唯一；暂不做浏览器持久化缓存；组合加载沿用普通立绘非阻塞流程；组合输出按普通图片进入 figure 控制系统。组件变体是后续扩展提案，当前只有 JSON 形状示例，没有可直接实现的完整规则。
